## The problem

Tailoring a resume to a specific posting works. It's also the most tedious part of a job search: read the description, work out which of your experiences actually map to it, rewrite the bullets in the posting's vocabulary, check everything still fits one page, repeat. Done honestly it takes twenty minutes a posting, so nobody does it a hundred times.

I wanted to know whether the whole loop could be automated without producing the generic LLM output a recruiter spots in three seconds — and without the pipeline collapsing the moment an external API had a bad day.

## How it works

Four agents on Google's Agent Development Kit, coordinated by a stateful orchestrator:

| Agent | Responsibility |
|---|---|
| **Discovery** | Pulls postings from Serper, Adzuna, and GitHub job boards |
| **Enrichment** | Scrapes the full description from each apply URL |
| **Analysis** | Embeds the JD and scores it against every resume component |
| **Generation** | Writes a tailored LaTeX resume from the selected components |

The orchestrator holds run state across all four, which is what makes caching and cross-stage deduplication possible rather than each agent caching in isolation.

## Decisions worth explaining

### A mock layer for every external dependency

`mock_search.py`, `mock_scraper.py`, and a mock embedding function, behind three orchestrator flags: `--mock` for the whole pipeline, `--mock-generation`, and `--mock-embeddings` for one stage at a time.

This is the decision I'd defend hardest. Every stage of this pipeline calls something that costs money, rate-limits, or is slow — search APIs, page scrapes, Gemini embeddings, Gemini generation. Without a mock path, every change to the LaTeX writer means burning quota on API calls that have nothing to do with what I'm testing, and a debugging session can exhaust a daily limit before lunch.

Being able to exercise the full pipeline offline meant the orchestration logic could be developed and debugged independently of the model calls. The per-stage flags matter more than the global one: mocking embeddings while generation stays real is exactly what you want when the thing you're debugging is prompt output.

### Caching keyed on what actually changes

Two caches with different invalidation strategies, because they're solving different problems.

The **embedding cache** is keyed on a hash of the resume file. My resume barely changes between runs, so re-embedding every component every time is pure waste — but the cache has to notice the moment I do edit it, and a file hash does that for free.

The **job cache** deduplicates postings by URL across runs, with a max-age so a listing that's been sitting in the cache for long enough gets treated as new again. Postings recur constantly across sources and across days; re-scraping and re-processing one I've already handled is the same waste at larger scale.

Together they turn a warm run into a fraction of a cold one. I have the timings from local benchmark runs, but the script is currently untracked — treat the speedup as unverified until it's committed alongside the code.

### Assuming the model produces invalid output

Generated resumes have hard constraints: bullets fit a length range, sections fit a bullet count, the whole thing fits a page. An LLM violates these regularly and no amount of prompt tightening drives the rate to zero.

So every generated resume is validated, and on failure the pipeline dispatches a **narrow repair prompt naming the specific violation** rather than regenerating from scratch. One repair attempt. If that also fails, the resume is written to `outputs/<date>/needs_review/` instead of being silently emitted or crashing the run.

The validator I'd point at first isn't the length check — it's `_validate_metric_preservation`, which extracts numeric claims from the master resume and confirms they survived into the tailored output intact. The failure mode it exists for is a model quietly rounding, dropping, or inventing a number while rewriting a bullet. On a resume that's not a formatting bug, it's a false claim about your own work, and it's the one error you cannot afford to ship.

## The failure I planned for, and the one I didn't

`retry_with_backoff` handles rate limiting: exponential backoff with jitter, and it parses the server's own suggested delay out of the error string (`"Please retry in 26.868412568s"`) and honors it when it's longer than the computed backoff. Quota exhaustion was the failure I expected on a pipeline making hundreds of model calls, so it's the one I built for.

Then a run hit a Gemini 503.

The retry path explicitly re-raises anything that isn't a rate-limit error, so a 503 isn't retried — it propagates. What caught it was the generic degradation path: the affected resumes routed to `needs_review`, completed work stayed completed, and the run produced usable output instead of a stack trace and an empty directory.

I want to be accurate about that rather than claim more credit than I'm owed. I designed a specific recovery for one failure mode and got a different one, and what saved the run was the decision to make partial results a first-class outcome instead of treating any error as fatal. That's the more useful lesson: the retry logic only helps with failures you predicted, and the degradation path is what covers the ones you didn't.

**The fix:** treat 503 and 500 as retryable alongside 429 — they're transient by definition. That's a two-line change to the `is_rate_limit` condition and a rename.

## What I'd do differently

**The profile doesn't generalize.** `yash_pathak.json` is hand-tuned — conditional triggers, importance tiers, exclude keywords. No real user is going to write `"include_if_jd_contains": ["reinforcement learning", "a* search", "mineflayer"]` for their own project. Most of it should be derived from the master resume: tech stack into triggers, resume order into default importance, header parsing into personal fields, leaving only genuinely personal input like location and visa status to a form.

**The parser only speaks LaTeX.** Extraction depends on structural markers — `\emph{}` for tech stack, `\resumeProjectHeading{}` for project boundaries. PDF and DOCX flatten those into plain text, where the stack might follow a pipe, sit in parentheses, or not be delimited at all. Supporting them is an architectural decision, not a patch.

**Nothing measures whether tailoring works.** I can measure how fast the pipeline runs and whether output is well-formed. I have no way to tell whether a tailored resume outperforms an untailored one — which is the premise the entire project rests on.

## What's next

A React and FastAPI web application with browser-based local persistence, turning JobScout from a tool I run locally into something other people can use without installing anything. Resume data stays in the browser, which sidesteps both the privacy question and the cost of storing other people's documents.
